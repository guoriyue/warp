  The FA3 Hopper kernel achieves peak throughput through several techniques that your current Warp implementation doesn't use. Here are the key gaps, ordered by expected impact:

  1. No compute/memory overlap (biggest gap)

  Your kernel is strictly sequential within the inner loop:

  load K → matmul QK^T → softmax (scalar) → load V → matmul PV → accumulate

  The FA3 kernel overlaps these via intra-warpgroup pipelining (IntraWGOverlap, line 1138-1252). Its fwd_step (line 1170) issues GEMM0 for block n, then GEMM1 for block n-1, then does softmax for block n — all interleaved with warpgroup_wait<1>() / warpgroup_wait<0>() to overlap the two matmuls:

  // FA3 fwd_step overlap pattern:
  flash::gemm(QK^T for block n);        // issue async
  flash::gemm(PV for block n-1);        // issue async, overlaps with above
  warpgroup_wait<1>();                    // wait for QK^T only
  // ... softmax for block n ...
  warpgroup_wait<0>();                    // wait for PV

  What you can do in Warp: Warp's tile_matmul calls WP_TILE_SYNC() after each matmul (tile.h:4622), so you can't overlap two matmuls within the current API. However, you can restructure the loop to overlap V loads with softmax computation:

  # so the load can overlap with softmax scalar work

  # Pre-load K[0]
  K_tile = wp.tile_load(...)

  for k_block in range(num_k_blocks):
      # QK^T matmul
      S_tile = wp.tile_zeros(...)
      wp.tile_matmul(Q_tile, K_T, S_tile)

      # Start V load NOW (before softmax) so memory latency overlaps with scalar work
      V_tile = wp.tile_load(V, ...)

      # Softmax (scalar per-thread work — overlaps with V load in flight)
      m_block_tile = wp.tile_reduce(wp.max, S_tile, axis=1)
      # ... online softmax ...

      # Pre-load K for NEXT iteration (overlaps with PV matmul setup)
      if k_block + 1 < num_k_blocks:
          K_tile_next = wp.tile_load(K, ...)

      # PV matmul
      PV_tile = wp.tile_zeros(...)
      wp.tile_matmul(S_tile, V_tile, PV_tile)

      K_tile = K_tile_next  # ready for next iter

  This won't give you the full GEMM-GEMM overlap that FA3 gets from async WGMMA, but it moves memory loads earlier so the hardware can hide latency behind the scalar softmax work.

  2. Per-thread scalar softmax is the bottleneck

  Your softmax (lines 188-195) does a scalar loop over TILE_N per thread:

  3. Output accumulator not in tile form

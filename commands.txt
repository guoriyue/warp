  Performance Analysis: FA3 Hopper vs. Your Warp Kernel

  The FA3 Hopper kernel achieves peak throughput through several techniques that your current Warp implementation doesn't use. Here are the key gaps, ordered by expected impact:

  1. No compute/memory overlap (biggest gap)

  Your kernel is strictly sequential within the inner loop:

  load K → matmul QK^T → softmax (scalar) → load V → matmul PV → accumulate

  The FA3 kernel overlaps these via intra-warpgroup pipelining (IntraWGOverlap, line 1138-1252). Its fwd_step (line 1170) issues GEMM0 for block n, then GEMM1 for block n-1, then does softmax for block n — all interleaved with warpgroup_wait<1>() / warpgroup_wait<0>() to overlap the two matmuls:

  // FA3 fwd_step overlap pattern:
  flash::gemm(QK^T for block n);        // issue async
  flash::gemm(PV for block n-1);        // issue async, overlaps with above
  warpgroup_wait<1>();                    // wait for QK^T only
  // ... softmax for block n ...
  warpgroup_wait<0>();                    // wait for PV

  What you can do in Warp: Warp's tile_matmul calls WP_TILE_SYNC() after each matmul (tile.h:4622), so you can't overlap two matmuls within the current API. However, you can restructure the loop to overlap V loads with softmax computation:

  # Restructured: load V for current block BEFORE softmax
  # so the load can overlap with softmax scalar work

  # Pre-load K[0]
  K_tile = wp.tile_load(...)

  for k_block in range(num_k_blocks):
      # QK^T matmul
      S_tile = wp.tile_zeros(...)
      wp.tile_matmul(Q_tile, K_T, S_tile)

      # Start V load NOW (before softmax) so memory latency overlaps with scalar work
      V_tile = wp.tile_load(V, ...)

      # Softmax (scalar per-thread work — overlaps with V load in flight)
      m_block_tile = wp.tile_reduce(wp.max, S_tile, axis=1)
      # ... online softmax ...

      # Pre-load K for NEXT iteration (overlaps with PV matmul setup)
      if k_block + 1 < num_k_blocks:
          K_tile_next = wp.tile_load(K, ...)

      # PV matmul
      PV_tile = wp.tile_zeros(...)
      wp.tile_matmul(S_tile, V_tile, PV_tile)

      K_tile = K_tile_next  # ready for next iter

  This won't give you the full GEMM-GEMM overlap that FA3 gets from async WGMMA, but it moves memory loads earlier so the hardware can hide latency behind the scalar softmax work.

  2. Per-thread scalar softmax is the bottleneck

  Your softmax (lines 188-195) does a scalar loop over TILE_N per thread:

  for n in range(TILE_N):
      s_val = float(S_tile[row, n]) * sm_scale_log2
      p = wp.exp2(s_val - m_new)
      S_tile[row, n] = wp.float16(p)
      l_block = l_block + p

  This is TILE_N sequential shared memory reads + writes + transcendental ops per thread. With TILE_N=64, that's 64 serial exp2 calls per thread per KV block.

  FA3 does softmax in registers on the GEMM accumulator (line 1155: softmax.online_softmax(tSrS)) — no shared memory round-trip. The scores stay in register fragments from GEMM0 output.

  What you can do in Warp: Use tile_map for element-wise operations on S_tile instead of scalar loops. This would let the tile infrastructure distribute the work across all threads rather than having each thread process one row sequentially:

  # Instead of per-thread scalar loop, use tile ops:
  # 1. Scale S_tile
  S_scaled = wp.tile_map(lambda x: wp.float16(float(x) * sm_scale_log2), S_tile)

  # 2. Row-wise max (you already do this)
  m_block_tile = wp.tile_reduce(wp.max, S_scaled, axis=1)

  # 3. Subtract max and exp2 via tile_map + tile_broadcast
  # (need to broadcast m_block_tile from (TILE_M,) to (TILE_M, TILE_N))
  # ... then compute P_tile = exp2(S_scaled - m_broadcast)

  # 4. Row-wise sum for l_block
  l_block_tile = wp.tile_reduce(wp.add, P_tile, axis=1)

  This keeps everything in the tile system and avoids the per-element shared memory indexing. Check if Warp supports tile_broadcast and tile_map with the patterns you need.

  3. Output accumulator not in tile form

  Your output accumulator is a per-thread wp.vector:
  o_acc = wp.vector(dtype=float, length=HEAD_DIM)

  After PV matmul, you read PV_tile[row, d] element-by-element (lines 208-209) — that's HEAD_DIM shared memory reads per thread per KV block.

  FA3 keeps tOrO as a register fragment that tile_matmul accumulates into directly (line 1182/1297: flash::gemm<zero_init=false>(..., tOrO)) with beta=1.

  What you can do in Warp: Use a tile as the accumulator and tile_matmul with beta=1.0 for accumulation:

  # Before loop:
  O_acc = wp.tile_zeros(shape=(TILE_M, HEAD_DIM), dtype=wp.float16, storage="shared")

  # In loop, after softmax:
  # Instead of tile_matmul into fresh PV_tile then per-thread copy:
  wp.tile_matmul(S_tile, V_tile, O_acc)  # accumulates if beta=1

  # For rescaling, use tile_map:
  # O_acc = O_acc * alpha  (via tile_map)

  Check if wp.tile_matmul(A, B, C) supports the alpha/beta parameters for C = alpha * A @ B + beta * C. If so, you can set beta=1.0 to accumulate.

  4. Multi-stage K/V pipelining (hardware-level)

  FA3 uses kStages (typically 2) pipeline stages (line 36, 283-289) with TMA async loads. While one K/V block is being consumed by MMA, the next is being loaded asynchronously into a different shared memory buffer. This completely hides global memory latency.

  What you can do in Warp: This requires double-buffering shared memory tiles, which Warp's current tile API doesn't directly support (tiles are allocated implicitly). This is more of a Warp framework feature request than something you can implement at the Python level today.

  5. Too few threads per block

  Your kernel uses block_dim = tile_m (32-64 threads = 1-2 warps). FA3 uses warpgroups of 128 threads (4 warps) or even 2-3 warpgroups (256-384 threads). More warps per SM means:
  - Better latency hiding (scheduler can switch warps during memory stalls)
  - Higher tensor core utilization (WGMMA uses full warpgroup)

  What you can do in Warp: Decouple block_dim from tile_m. Use block_dim = max(128, tile_m) and guard per-thread operations with if row < TILE_M. This was the fix for the tile_m=16 error but also applies as a general performance improvement. More threads means the cuBLASDx GEMM has more parallelism.

  6. Scheduler barrier hints

  FA3 uses warp_scheduler_barrier_sync/arrive (lines 1176, 1183, 1256, 1336) to hint the hardware warp scheduler, improving instruction-level parallelism. This is SM90-specific.

  Not directly available in Warp — would need native support.
